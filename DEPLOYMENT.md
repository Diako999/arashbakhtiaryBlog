# Deployment (Windows + IIS + SQL Server)

This app is a single deployable: ASP.NET Core serves both the `/api/*`
endpoints and the built React static files. There is no separate frontend
host, no Docker, and no Linux-specific step in this document — everything
below assumes a Windows Server host with IIS.

## 1. One-time server setup

1. Install the **.NET 8 Hosting Bundle** (not just the runtime) from
   https://dotnet.microsoft.com/download/dotnet/8.0 — this installs the
   ASP.NET Core Module (ANCM) that lets IIS reverse-proxy to Kestrel. Restart
   IIS afterward (`net stop was /y` then `net start w3svc`), or reboot.
2. Make sure IIS has the **Web Server (IIS)** role with the standard
   modules; no extra IIS feature is needed beyond ANCM.
3. Have a SQL Server instance reachable from this host (local install or a
   separate DB server). Create a login + database for the app, e.g.:

   ```sql
   CREATE LOGIN arashblog_app WITH PASSWORD = 'CHANGE_ME';
   CREATE DATABASE ArashBlogProd;
   USE ArashBlogProd;
   CREATE USER arashblog_app FOR LOGIN arashblog_app;
   ALTER ROLE db_owner ADD MEMBER arashblog_app;
   ```

   `db_owner` is simplest for now since EF Core migrations run against this
   same database; tighten later if desired.

## 2. Build

From the repo root, on any machine with the .NET 8 SDK and Node.js
installed (does not have to be the server itself):

```powershell
# Frontend — builds into src/ArashBlog.Api/wwwroot (see vite.config.ts)
cd src/arashblog-web
npm ci
npm run build
cd ../..

# Backend — publish self-contained framework-dependent output
dotnet publish src/ArashBlog.Api/ArashBlog.Api.csproj -c Release -o publish
```

`npm run build` must run **before** `dotnet publish`, and its output
(`wwwroot`) is picked up automatically since it lives under
`src/ArashBlog.Api`. The `publish/` folder now contains everything IIS
needs — copy it to the server (e.g. `C:\inetpub\arashblog`).

## 3. Configure the site on the server

1. Copy `appsettings.Production.json.example` to `appsettings.Production.json`
   next to the published DLL, and fill in the real connection string. This
   file is git-ignored on purpose — it holds production secrets and must
   never be committed.
2. Prefer environment variables over the file for the two secrets that
   matter most (`ConnectionStrings__DefaultConnection` and the
   `InitialAdmin__*` pair below) if this host is shared or backed up
   anywhere the file's contents could leak. ASP.NET Core's configuration
   system overlays environment variables on top of the JSON file
   automatically — no code change needed either way.
3. In IIS Manager, create a new **Application Pool**:
   - .NET CLR version: **No Managed Code** (Kestrel handles the runtime,
     not IIS's CLR host)
   - Start mode: AlwaysRunning (avoids a slow first request after idle)
4. Create a new **Site** pointing at the `publish` folder, bound to the
   app pool above. A `web.config` is already generated by `dotnet publish`
   inside `publish/` — it wires up the ASP.NET Core Module; no manual
   edits are normally needed unless you're customizing the process path.
5. Set `ASPNETCORE_ENVIRONMENT=Production` as an environment variable on
   the site (IIS Manager → site → Configuration Editor →
   `system.webServer/aspNetCore` → environmentVariables), or in
   `web.config` directly. Without this, the app runs its Development
   defaults (Swagger UI exposed, no HSTS/HTTPS-redirect, no secure-cookie
   flag) — all of that logic in `Program.cs` is gated on
   `IsProduction()`.

## 4. Apply database migrations

Run this once per deploy that adds new migrations (from a machine with the
.NET SDK and network access to the SQL Server instance — does not have to
be the IIS host itself):

```powershell
dotnet tool install --global dotnet-ef   # if not already installed
dotnet ef database update `
  --project src/ArashBlog.Api/ArashBlog.Api.csproj `
  --connection "Server=YOUR-SQL-SERVER-HOST,1433;Database=ArashBlogProd;User Id=arashblog_app;Password=CHANGE_ME;TrustServerCertificate=False;Encrypt=True;"
```

The app itself never runs migrations automatically in Production — only
the unconditional, idempotent seeders (`NavItemSeeder`, `FlatPageSeeder`)
run on every startup, and those only insert rows, never alter schema.

## 5. First admin login

There is no self-service registration or `createsuperuser`-style CLI
command by design — this app has exactly one admin account, matching how
the original Django project only ever had one dashboard user. To create it
on first boot, set these two config values (env vars recommended, same as
the connection string):

```
InitialAdmin__Username=admin
InitialAdmin__Password=<a real password, not the placeholder>
```

`AdminBootstrapper` (wired into `Program.cs`, runs on every startup) checks
whether any user row exists; if none does **and** both values above are
set, it creates that one admin account. Once any user exists it becomes a
permanent no-op, so it's safe to leave these variables in place indefinitely
— but rotating/removing the password value after the first successful boot
is good practice regardless.

After first login, complete TOTP 2FA setup (QR code shown once, recovery
codes shown once) before the account can reach the dashboard — this is
enforced the same way for every login, not skippable in Production.

## 6. Media uploads

Uploaded images/PDFs are stored outside `wwwroot` at
`<ContentRoot>/media` (created automatically at startup if missing) and
served at `/media/*`. On IIS, `<ContentRoot>` is the folder containing the
published DLL (`publish/` from step 2) — make sure the app pool's identity
has write access to that folder, or uploads will fail with a permissions
error rather than a validation error.

If this folder needs to survive redeploys (it should — it holds real user
uploads, not build output), point it outside the folder you overwrite on
each deploy: either redeploy by copying new files over the old `publish/`
folder in place (never delete-and-recreate it), or override the media path
to a stable location outside `publish/` entirely if the deploy process ever
changes to a swap-the-whole-folder model.

## 7. HTTPS / firewall

- Terminate TLS at IIS (a certificate bound to the site in IIS Manager) —
  `Program.cs` already handles the reverse-proxy case
  (`UseForwardedHeaders` before `UseHttpsRedirection`/`UseHsts`), matching
  Django's `SECURE_PROXY_SSL_HEADER` setup.
- Open port 443 (and 80 only if you want the automatic HTTP→HTTPS
  redirect to work rather than blocking HTTP outright) on the Windows
  Firewall and any network firewall in front of the host.
- `AllowedHosts` in `appsettings.Production.json` should be the real
  domain(s), not `*` — ASP.NET Core rejects requests with an unrecognized
  `Host` header otherwise.

## 8. Smoke test after deploy

1. Visit the site over HTTPS, confirm the React app loads (not the
   fallback plain-text message from `Program.cs`, which means `wwwroot`
   is empty — the frontend build didn't happen or didn't get copied).
2. Log in as the admin, complete 2FA setup, reach the dashboard.
3. Create a post, upload a cover image, confirm it renders at its
   `/media/...` URL.
4. Hit `/api/blog/posts` a dozen times rapidly and confirm a 429 shows up
   eventually (rate limiting is live) — do this once per deploy, not as a
   standing health check, since it's disruptive to trip on purpose.
